REAL-TIME BYTECODE EXECUTION

From Telegram Packet to Room Speaker Audio

Scroll down to scrub through the 4 on-device hardware execution phases:

PHASE 01 // INGRESS
Adaptive Long Polling

Device maintains long-poll socket via OkHttpClient. If Wi-Fi disconnects, AdaptiveBackoff suppresses 80%+ of CPU wakeups until connectivity resumes.

PHASE 02 // EXECUTION
In-Memory Ring Buffer

State events pass into a synchronized in-memory ring buffer. 0 bytes written to flash storage during continuous polling, protecting phone flash memory from burnout.

PHASE 03 // RESOLUTION
AudioStreamResolver

Extracts audio stream via yt-dlp API proxy or tunes to 6 high-bitrate zero-buffer internet radio stations. Hardware MediaPlayer initializes asynchronously.

PHASE 04 // EGRESS
Dual Playback Delivery

Audio streams physically through phone speakers via AudioManager AND uploads directly to Telegram chats via sendAudio with scrub timeline & artwork.

Why I Built TapBot

> I had an old Android smartphone sitting in my desk drawer doing nothing.

> That device already had an 8-core ARM processor, a lithium battery backup, Wi-Fi, 4G cellular fallback, and audio hardware. Yet every month I was paying \$15 to \$30 to cloud VPS providers to host simple Telegram bots.

> TapBot was built to reclaim that computing power. By compiling bots for native Android ART bytecode and protecting flash storage with in-memory ring buffers, an old phone becomes an immortal, silent, self-hosted hardware server.
